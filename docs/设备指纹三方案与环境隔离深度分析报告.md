## 1. 环境隔离体系架构（修改前基线）

### 1.1 三层隔离

2Box 的"环境"（Env）是**进程级沙箱**，由三层机制叠加：

```
┌─ 进程层：DLL 注入（Detours）
│    2Box ──DetourCreateProcessWithDllExW──▶ cmd.exe（注入 MemoryDll）
│      cmd.exe 的 CreateProcessW hook 递归注入所有子进程（如 WXWork.exe）
│
├─ 文件层：NT 路径重定向（Hook-Ntdll）
│    NtCreateFile / NtOpenFile / NtSetInformationFile
│    命中 6 个 Known Folder → 重写到 exeDir\Env\<idx>\<相对路径>
│    源文件缺失 → RPC 请求 2Box 拷贝原生源文件（createRedirectFile）
│
└─ 注册表层：应用 hive 双写（Hook-Ntdll 注册表 hook）
     NtSetValueKey   → 真实注册表 + appKey hive 双写
     NtQueryValueKey → 优先查 appKey hive，失败回退真实注册表
```

### 1.2 重定向的 6 个文件夹

| Known Folder | 作用 |
|---|---|
| `%LocalAppData%` | 应用本地数据、CEF 缓存 |
| `%LocalAppDataLow%` | 低完整性进程数据 |
| `%RoamingAppData%` | 登录态、配置（WXWork 写这里） |
| `%ProgramData%` | 全局数据（**qimei 在这里**） |
| `%Documents%` | WXWork user-data-dir 落点 |
| `%SavedGames%` | 游戏存档 |

> 注：`microsoft / nvidia / amd / \2box\env\` 路径**白名单排除**，避免 hook 自身死循环与系统关键数据污染。

### 1.3 注入链路

```
2Box: DetourCreateProcessWithDllExW(cmd.exe, "/c start "" app.exe", DLL=MemoryDll64)
  └─ cmd.exe DLL_PROCESS_ATTACH → biz_initialize(envFlag, envIndex, rootPath)
       ├─ initialize_global_data：注册表/自身路径/Known Folder 初始化
       ├─ initialize_rpc：RPC 登录 2Box（失败 → TerminateProcess 自毁）
       └─ initialize_hook：安装全部 hook
  └─ cmd.exe CreateProcessW hook 递归注入 app.exe（同一条注入链）
```

## 2. 设备指纹三方案技术实现（本次修改）

### 2.1 方案 1：Local State 环境内自生成（machine_id 指纹）

**问题**：Chromium/CEF（WXWork 内核）的 `Local State` 含 `machine_id`、hardware 指纹。原逻辑源文件缺失时由 2Box RPC 把**原生** `Local State` 拷贝进环境 → 所有环境共享同一 machine_id → 风控判定"同一台设备的批量账号"。

**改动**：[FileRedirect.cpp](file:///d:/Projects/2Box-master/2Box/biz/file_redirect/FileRedirect.cpp) 新增 `is_fingerprint_file`：

```cpp
bool is_fingerprint_file(const std::wstring& redirectFile)
{
    if (fileName == L"Local State")            return true;   // Chromium machine_id
    if (lower 含 "tencent\\qimei")             return true;   // 腾讯 qimei 指纹
    return false;
}
```

命中则 `create_redirect_file` 直接返回，**不拷贝原生文件**。环境内首次访问时文件不存在 → Chromium 自生成全新 `machine_id`，并随环境目录持久化。

**能力**：
- 每个环境独立 `machine_id`，互不共享，重启不变（文件在环境目录内）
- 与方案 2（注册表）互补：Chromium 的 machine_id 落文件，注册表指纹落 hive

**局限**：若 Chromium 在 `Local State` 之外还使用其它指纹（如 `Preferences` 中的 `"hardware"` 段、`origin_bound_certs`），仍可能携带少量原生信息。后续可扩展黑名单。

### 2.2 方案 2：注册表环境持久化（hive 落盘 + 隔离）

**问题**：原实现 `RegLoadAppKeyW` 加载的是**16KB 易失空 hive，永不落盘**——各环境注册表写操作只存在于进程内存，进程退出即丢，环境"指纹"每次重启都是新的，且环境间完全独立但**无法持久化**（登录态、设备指纹的注册表部分反复重置）。

**改动**（hive 生命周期重构）：

```
2Box 主进程（elevated）:
  Env::loadRegistryHive()   RegLoadKeyW(HKU\2Box_Env_<idx>, hive文件)
                            · 首次：create_empty_hive_file 建空 hive
                            · 已损坏：重建空 hive 再加载（兼容旧版 RegLoadAppKeyW 临时 hive）
  Env::saveRegistryHive()   RegSaveKeyW → .tmp（hive 加载期间文件被锁，不能直接覆盖）
  Env::unloadRegistryHive() RegUnLoadKeyW → 释放文件锁 → commitPendingHiveFile（.tmp 原子替换正式文件）

DLL 侧（每个环境进程）:
  Data::initializeRegistry()  直接 RegOpenKeyExW(HKEY_USERS, "2Box_Env_<idx>", KEY_ALL_ACCESS)
  is_app_key_name 前缀改为 \REGISTRY\USER\2Box_Env_（避免 hook 自递归）
```

**保存时机**：
| 时机 | 动作 |
|---|---|
| 环境进程启动前（Launcher） | `loadRegistryHive`（幂等，已加载直接复用） |
| 环境内进程全部退出 | `saveRegistryHive` 检查点（**不卸载**，见 §5） |
| 2Box 正常退出（Core 析构） | 全部环境 `save + unload + commit` |
| 删除环境（deleteEnv） | 先 `unload` 再删目录（否则 hive 文件被系统锁定） |

**能力**：
- 环境注册表数据随环境持久化，重启恢复，指纹稳定
- 环境间完全隔离（各环境独立 `HKU\2Box_Env_N`）
- 每次落盘走 `.tmp + rename` 原子替换，避免写坏 hive

**局限/依赖**：
- `RegLoadKeyW`/`RegSaveKeyW` 需要 `SeRestorePrivilege`/`SeBackupPrivilege` → **2Box 必须以管理员运行**（当前程序自我提权，OK）
- hive 加载期间**无法直接覆盖文件**（系统锁），必须卸载后提交（已处理）
- 2Box 被强杀（任务管理器）时 hive 仍留在 HKU，下次启动直接复用内存副本，数据不丢；但若**系统重启**且 2Box 未正常退出，上次会话的注册表写入会丢（由下次首启重新生成指纹）

### 2.3 方案 3：qimei 设备指纹目录独立

**问题**：腾讯系应用的 qimei（设备标识）写 `C:\ProgramData\Tencent\qimei`。原逻辑缺失时拷贝原生 qimei → 所有环境同一个 qimei。

**改动**：`is_fingerprint_file` 命中 `tencent\qimei` 路径 → 不拷贝。环境内 `Env\<idx>\ProgramData\Tencent\qimei` 由腾讯组件自行生成**独立唯一** qimei。

**能力**：环境间 qimei 正交；qimei 是腾讯风控核心指纹之一，此改动直接降低"同机多号"判定。

**局限**：qimei 生成依赖腾讯组件内部逻辑；若组件有机器级硬编码信息参与生成，仍可能带上部分真机特征（概率低，通常 qimei 基于随机数）。

## 3. 修改前后对比

| 维度 | 修改前 | 修改后 |
|---|---|---|
| Local State / machine_id | 所有环境共享原生同一份 | 每环境独立自生成、持久化 |
| qimei | 所有环境共享原生同一份 | 每环境独立生成 |
| 注册表持久化 | `RegLoadAppKeyW` 易失 hive，重启即丢 | `RegLoadKeyW` 落盘 hive，重启恢复 |
| 注册表隔离 | 每进程独立 app hive | 每环境共享 `HKU\2Box_Env_N`（多进程一致） |
| 环境指纹稳定性 | 不稳定（每次重启新指纹） | 稳定（文件 + hive 双持久化） |
| 权限要求 | 无需管理员 | 需要管理员（自我提权，已满足） |
| 子进程初始化 | 自包含，无外部依赖 | 依赖 hive 已加载（本次已修复竞态） |

## 4. 封号检测概率分析

### 4.1 风控检测面与覆盖度

| 指纹维度 | 原状态（共享） | 新状态（隔离） | 风控权重（估） |
|---|---|---|---|
| machine_id（Local State） | ❌ 全环境相同 | ✅ 独立 | ★★★★ |
| qimei（ProgramData） | ❌ 全环境相同 | ✅ 独立 | ★★★★★ |
| 注册表指纹（HKU hive） | ⚠️ 每次重启变化 | ✅ 独立且稳定 | ★★★ |
| 浏览器/CEF 指纹（UA/Canvas/WebGL） | ⚠️ 取决于注入范围 | 部分隔离 | ★★★ |
| **IP 地址** | ❌ 所有环境同出口 | ❌ 未覆盖（需代理/IP 池） | ★★★★★ |
| **设备代理/TLS 指纹** | ❌ 未覆盖 | ❌ 未覆盖 | ★★★★ |
| 登录行为（频次/时段/设备数） | 部分 | 部分改善 | ★★★ |

### 4.2 结论

- 文件 + 注册表 + qimei 三维度**环境间完全正交**后，同一环境同一账号"退出重登"指纹不变 → 不再误判为"新设备"，**大幅降低验证码与封号**。
- 不同环境不同账号 → 风控看到的是**不同设备**，批量多开不再共享指纹 → 消除"一台真机挂 N 个号"的最高危信号。
- **剩余最大风险是网络层**（所有环境共用出口 IP）。多环境高频操作同一 IP 仍是风控强信号；若要进一步降低，需配合每环境独立代理（IP 池），本方案未覆盖，属后续规划。

> 概率量化（估算，非官方）：共享指纹阶段，多环境同号同机信号被风控命中的概率显著高于独立指纹；独立后**单环境单账号正常使用**的封号概率趋近于真机单开水平，主要残余风险转移至网络层与行为层。

## 5. 本次"启用进程后秒退出"Bug 根因与修复

### 5.1 现象

启动环境 2（WXWork）后 1 秒内进程全部退出：
- cmd.exe 每次都成功"接入环境"（登录成功）
- WXWork.exe 从未出现"接入环境"日志，无任何 WXWork 日志写入，无 WER 崩溃记录（`TerminateProcess` 不产生转储）
- 两次启动（02:34:11 / 02:34:17）行为完全一致

### 5.2 根因链

```
我引入的改动：removeProcessInternal 在进程数归零时 saveRegistryHive() + unloadRegistryHive()
                                  └──────────┬─────────┘
        cmd /c start "" "WXWork.exe" 模式：cmd.exe 创建 WXWork 后【立即退出】（不等它）
                                            │
                     cmd 退出 → 进程数 1→0 → 立即 RegUnLoadKeyW 卸载 HKU\2Box_Env_2
                                            │
        WXWork 仍在 DLL_PROCESS_ATTACH → initializeRegistry → RegOpenKeyExW(HKU\2Box_Env_2)
                                            │ 失败（hive 已被卸载）
                                            ▼
        biz_initialize catch → TerminateProcess(WXWork)      ← "秒退出"
        （或 hook 的 inject_dll_to_process 检测到 DllMain 返回 FALSE → TerminateProcess）
```

**为什么 cmd 每次都成功**：cmd 是 2Box 启动的第一个进程，执行时 hive 刚被 `loadRegistryHive` 加载，必然可打开。
**为什么旧版没问题**：旧版 DLL 用 `RegLoadAppKeyW`（每进程私有、直接读文件），完全不依赖 HKU 中 hive 的存在，无此竞态。

### 5.3 修复

[Env-Envrironment.cpp](file:///d:/Projects/2Box-master/2Box/biz/env/Env-Envrironment.cpp) `removeProcessInternal`：进程归零时**只保存、不卸载**。

```cpp
// 注意：不能在此卸载 hive！cmd /c start 启动应用时 cmd 会立即退出，
// 若此时卸载 hive，正在初始化的子进程（如 WXWork）将无法打开
// HKU\2Box_Env_<idx> 而被 TerminateProcess 秒杀。
if (removed && remaining == 0)
{
    saveRegistryHive();   // 仅保存检查点
}
```

hive 生命周期修正为：**加载后保持到 2Box 退出**（Core 析构统一 save+unload+commit），删除环境时单独 unload。文件锁与覆盖问题通过 `.tmp 写入 → 卸载后原子 rename` 解决。

### 5.4 验证方式

- 启动环境 2 → WXWork 正常出窗、正常登录（DLL 初始化不再被秒杀）
- 观察 `bin\x64\Env\2\<flag>` 文件在进程退出后仍保持（hive 持续加载，不再反复卸载）
- 2Box 正常退出后，hive 文件被最终提交（LastWriteTime 更新）

## 6. 已知限制与风险清单

| # | 风险/限制 | 影响 | 建议 |
|---|---|---|---|
| 1 | 网络层未隔离（IP 共用） | 多环境多号仍共享出口 IP | 每环境独立代理/IP 池（后续） |
| 2 | 2Box 强杀 + 系统重启 | 未落盘的注册表写入丢失，指纹重置 | 周期保存（如进程活动期间每 60s save）；接受低概率重置 |
| 3 | 管理员权限强依赖 | 非管理员运行则 `RegLoadKeyW` 失败（1314） | 保持自我提权；启动时校验并提示 |
| 4 | 项目根目录存在嵌套旧副本 `2Box-master\2Box-master`（含陈旧源码/产物） | 易混淆、占空间、可能被误构建 | 建议清理删除，仅保留根 `2Box/`、`MemoryDll/`、`common/` 等 |
| 5 | 指纹文件黑名单覆盖有限 | 除 Local State / qimei 外可能有其它指纹载体 | 按需扩充 `is_fingerprint_file` |
| 6 | hive 双写性能 | 每次注册表写多一次 appKey 写 | 可接受（低频操作） |
| 7 | 旧环境 flag 文件（旧版 RegLoadAppKeyW 临时 hive） | 与 `RegLoadKeyW` 不兼容 | 已实现"重建空 hive"回退，旧文件自动替换 |

## 7. 后续建议（可选）

1. **网络层隔离**：为每个环境配置独立 HTTP 代理（本地 SOCKS5/HTTP 端口池），覆盖 IP 维度，是封号概率最大的进一步降幅。
2. **指纹文件黑名单扩展**：监测 WXWork 实际写入的指纹载体（如 `Preferences`、`origin_bound_certs`、`SNBD` 等），按需加入 `is_fingerprint_file`。
3. **注册表周期保存**：进程存活期间每 N 分钟 `RegSaveKeyW` 一次，把 2Box 强杀时的数据丢失窗口收窄到 N 分钟。
4. **hive 健康检查**：`loadRegistryHive` 失败时给出明确 UI 提示（权限不足/文件损坏），避免静默降级。
5. **清理嵌套旧副本** `2Box-master\2Box-master` 目录，避免后续构建/排查混淆。
