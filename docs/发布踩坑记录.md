# eBox 发布版本踩坑记录

> 每次发布新版前必读。本文件记录发布过程中踩过的坑与正确做法，避免重复踩坑。
> 发布命令入口：`.\publish_v2.x.ps1`（含中文，见下方"编码坑"）。

---

## 一、版本号必须多处同步修改（一个都不能漏）

版本号是**分散常量**，虽然 `MainApp.ixx` 注释写"单一可信源"，但其它文件是**硬编码**，需要人工同步。漏改会导致：
- 客户端版本比较错乱（升级判断失效 / 反复提示更新）
- 授权/激活校验与版本不一致
- `.rc` 版本信息与程序内版本不一致（任务管理器/属性里显示旧版本）

发布前核对这 4 处：

| 文件 | 位置 | 内容 |
|---|---|---|
| `eBox/app/MainApp.ixx` | 顶部常量 | `kVerMajor / kVerMinor / kVerPatch / kVerCode / appVersion / appUpdateDate` |
| `eBox/res/eBox.rc` | `VERSIONINFO` | `FILEVERSION 2,9,8,20908` + `VALUE "FileVersion", "2.9.8"` 等字符串 |
| `eBox/biz/license/License.cpp` | `kAppVersion[]` | 如 `L"v2.9.8"` |

> **verCode 规则**：`major*10000 + minor*100 + patch`（如 2.9.8 → 20908）。
> 该规则与 `.github/scripts/update_manifest.py` 中 `version_code` 计算方式**必须一致**，
> 否则客户端 `latestVersionCode` 与服务端 update.json 的 `latestVersionCode` 语义不同。

## 二、PowerShell 中文脚本编码坑（最隐蔽，最常踩）

**现象**：含中文的 `.ps1`（发布脚本、release body 中文字符串）执行报：
```
String missing terminator: '@
```
或 here-string 断句错误。

**原因**：Windows PowerShell 5.1 对**无 BOM** 的 `.ps1` 默认按 **System ANSI（GBK）** 解析。
脚本里的 `@'...'@` 中文字符在 GBK 下被读成不同字节，导致 `'@` 结束符被吞掉。

**正确做法**：写含中文的 `.ps1` 时，**必须保存为带 UTF-8 BOM** 的编码：
```powershell
[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding $true))
```
> 旧的 `Set-Content -Encoding UTF8` 在 PS 5.1 下写出来是 **无 BOM** 的，同样会触发该问题。
> 用 VS Code 保存时选 "UTF-8 (with BOM)"，或统一用上面的 API 写。

## 三、发布产物 source 与一致性

- 发布上传的是 `bin\x64\eBox.exe`；仓库里通常还留有历史版本 `eBox-2.9.5.exe / eBox-2.9.7.exe / eBox-2.9.8.exe`。
- 必须保证**上传的 exe 与 `bin\x64\eBox.pdb` 是同一构建**（PDB GUID 一致），否则：
  - 客户端拿到我们发的崩溃 dump 时无法用该 PDB 符号化；
  - `update.json` 的 `downloadSha256` 与本地构建对不上（会校验失败）。
- 发布前可在 VS 重新构建 Release x64 后再复制 / 直接以 `bin\x64\eBox.exe` 上传。

## 四、发布脚本要点（`.publish_v2.x.ps1`）

- **token 获取**：通过 `git credential fill`（`protocol=https` + `host=github.com`）从 git 凭据取 GitHub token，需 `WaitForExit` 超时保护。
- **建 Release**：`POST /repos/{repo}/releases`，body 用 `ConvertTo-Json`。
- **传资产**：`POST https://uploads.github.com/repos/{repo}/releases/{id}/assets?name=eBox.exe`，
  `ContentType 'application/octet-stream'` + `-InFile $exe`。
- 输出 `release_id` / asset id / size，便于后续核对。

## 五、GitHub Actions 自动更新（release published 触发）

工作流：`.github/workflows/auto-update.yml` + `.github/scripts/update_manifest.py`

触发：`release: types: [published]`（**发布后**自动跑）。

流程与坑：
1. **下载资产带 60s 容忍重试**：容忍"先建 Release 后传 exe"。用 `gh release download --pattern "*.exe"`，需 `GH_TOKEN`。
2. **从 tag 解析版本**：`vX.Y.Z`；`version_code = major*10000 + minor*100 + patch`。
3. **changelog**：从 Release body 逐行提取，去掉 markdown 列表前缀 `-/ * / #`。
4. **写 `dist/update.json` 必须 `ensure_ascii=False` + `encoding="utf-8"`**：changelog 含中文，否则变 `\uXXXX`。
5. **读 manifest 用 `encoding="utf-8"`**，并**保留其它字段**（`minSkipVersionCode / forceUpdate`），不要覆盖丢掉。
6. **提交前先 `git diff --cached --quiet` 判断是否变更**：无变更则跳过 commit，避免 `git commit` 空提交失败。
7. **Purge jsDelivr CDN 是必须的**：客户端走 `cdn.jsdelivr.net/gh/shushuhao01/ebox@main/dist/update.json`，
   不 purge 会拿到旧缓存。用
   `curl -s "https://purge.jsdelivr.net/gh/shushuhao01/ebox@main/dist/update.json" || true`，
   purge 可能限流，用 `|| true` 容忍失败，但**失败要人工重试**，否则用户更新不了。
8. `update.json` 的 `downloadUrl` 指向 GitHub release 资产链接：`https://github.com/shushuhao01/ebox/releases/download/{tag}/{exe_name}`。
9. **Actions 串行/冲突**：连续多次发布时，Actions 之间可能抢占 main → 建议一次只发一个版本；若上一条 update 尚未 push 完，别立刻发下一条。

## 六、发布前检查清单

- [ ] 版本号是否在 `MainApp.ixx / eBox.rc / License.cpp` 三处全部同步？
- [ ] `kVerCode` 是否 = `major*10000 + minor*100 + patch`？
- [ ] 发布脚本 `.ps1` 是否保存为 **UTF-8 with BOM**？
- [ ] `bin\x64\eBox.exe` 与 `eBox.pdb` 是否是同一构建（GUID）？
- [ ] 上传资产名是否为 `eBox.exe`？
- [ ] `dist/update.json`（本地版本）是否与 Actions 生成规则一致？
- [ ] 发布后是否确认 Actions 成功 + jsDelivr 已 purge？（可请求 `https://purge.jsdelivr.net/...`）
