# eBox 官网设计与实现方案

> 目标：一套「前台展示 + 后台可管」的官网系统，承接品牌展示、功能介绍、使用案例、下载、购买转化，并让运营能自主更新内容、发布版本、配置站点与安全策略。
>
> 关联文档：[授权服务平台方案.md](./授权服务平台方案.md)、[宝塔部署.md](./宝塔部署.md)、[eBox使用手册.md](./eBox使用手册.md)、[用户协议.md](./用户协议.md)

---

## 一、目标与定位

| 维度 | 定位 |
|---|---|
| 对用户 | 官网是「第一印象」：3 秒内看懂 eBox 是什么、好在哪、怎么下载、怎么买 |
| 对搜索 | 承接「电脑多开」「企业微信多开」「多开器」等长尾搜索，做 SEO 落地页 |
| 对运营 | 后台自助更新文章 / 公告 / 版本 / 站点配置，不依赖开发改代码发版 |
| 对转化 | 两条主链路：**免费下载试用 → 引导购买**、**直接购买（发卡商城）** |
| 与现有系统 | 复用授权平台的可复用部分（后端服务、后台框架、账号体系、部署链路），不重复造轮子 |

**核心设计原则**

1. **单一数据源**：版本与下载信息只认 `dist/update.json` + GitHub Release，官网只做展示，绝不后台手填造成「官网版本和客户端实际版本不一致」。
2. **不碰授权链路**：官网的任何改动、维护模式、限流策略，都不能影响客户端 `/api/v1/*`（授权/心跳），否则会误伤所有已付费用户。
3. **内容即配置**：所有会变的文案（标题、价格、版权、公告、联系方式）都进后台，不进代码。

## 三、整体架构

```
                          ┌─────────────────────────────┐
   访客浏览器  ──https──►  │  Nginx (abc222.cn :443)      │
                          │   /            → 官网前台     │
                          │   /admin/      → 管理后台     │
                          │   /api/        → 127.0.0.1:3008
                          └──────────────┬──────────────┘
                                         │
                          ┌──────────────▼──────────────┐
                          │ Express 后端 (PM2 :3008)      │
                          │  /api/v1/*      客户端授权（不动）
                          │  /api/admin/*   管理接口
                          │  /api/site/*    官网公开只读接口（新增）
                          │  /api/admin/site/* 官网管理接口（新增）
                          └──────────────┬──────────────┘
                                         │
                          ┌──────────────▼──────────────┐
                          │  MySQL 8 (同一实例/同库)      │
                          │  授权表 + 官网表（site_*）    │
                          └─────────────────────────────┘

   eBox 客户端 ──https──► /api/v1/*  （与官网完全隔离，不受官网维护模式影响）
```

**关键决策：官网与授权平台共用一套后端与后台**。理由：一次部署、一套账号权限、一套日志与限流，运维成本最低；缺点是耦合，用「接口前缀隔离 + 独立数据表」把风险降到最低。

| `/404`、`/maintenance` | 兜底 | 404、维护中（由后台开关控制） |

### 4.2 首页结构（从上到下）

1. **顶部导航**：Logo｜功能｜案例｜下载｜购买｜文档｜联系｜【免费下载】
2. **公告条**（后台可开关）：最新版本 / 活动公告，可关闭
3. **首屏 Hero**：一句话价值主张（如「一台电脑，多开任意应用」）+ 副标题 + 【立即下载】【查看功能】双按钮 + 软件界面截图/动图
4. **信任条**：已服务用户数 / 稳定运行时长 / 版本号 / 支持系统（数据来自后台可配）
5. **核心卖点 3~4 卡**：不是虚拟机 · 环境独立隔离 · 免扫码自动登录 · 体积小不卡顿
6. **功能图解**：用「简约版手册 12 步」做分步图示（横向滚动/分屏）
7. **对比表**：强开 / 虚拟机 / eBox（复用第二篇对比表）
8. **使用案例**：3 张卡片 + 「查看更多」
9. **下载 + 购买 CTA 区**：左下载（自动显示最新版本）/ 右购买（跳商城）
10. **页脚**：站点信息、导航、联系方式、协议、ICP 备案、公安备案、版权（全部后台可配）

### 4.3 「下载」页逻辑（重要）

```
页面加载 → 读 GET /api/site/latest-release
        → 后台返回 { latestVersion, releaseDate, downloadUrl, downloadSize, changelog, sha256 }
        → 主按钮：直连下载（GitHub Release / 备用镜像，后台可配优先级）
        → 副按钮：网盘 / 镜像站（后台可配，解决 GitHub 国内慢）
        → 展示：版本号、更新日期、文件大小、SHA-256（供校验）、更新日志（逐条）
```

- **主按钮不写死 URL**：由 `latest-release` 接口下发，保证换 CDN / 加镜像时无需改前端。
- **版本更新流程不变**：仍走 GitHub Release → Actions 自动更新 `update.json`；官网仅**读取展示**，后台只做「同步/刷新」动作，不提供编辑入口（避免双写不一致）。

### 4.4 购买链路（外部跳转，无商城功能）

- **官网不做任何商城功能**：不展示价格、不做套餐对比、不集成支付。
- 发卡商城是**独立站点**（noepay.cn），官网只负责「跳过去」，本期**不开发商城相关功能**。
- 实现方式：后台「**网站设置**」配置一个 `purchase_url`（购买入口地址）；前台所有「立即购买 / 购买会员」按钮统一读取该地址，**新窗口打开**。
- 更换发卡平台时，只需后台改配置，前端零改动。
- 未完成购买的引导：下载页 / 客服 / 手册（避免用户卡在「买了之后干嘛」）。

## 六、访问与安全策略（后台可配）

按「影响范围」分为三档，**默认全关**，开启前有明确的二次确认与影响提示。

### 6.1 站点可见性

| 策略 | 说明 | 注意 |
|---|---|---|
| 维护模式 | 官网前台统一跳到 `/maintenance`，后台仍可登录 | **只拦截官网路由与 `/api/site/*`，绝不拦截 `/api/v1/*`** |
| 灰度放行 | 维护模式下按 IP 白名单放行（便于自己预览） | 白名单与下面的 IP 策略共用 |
| 访问口令 | 全站需要口令才能浏览（用于内测发布） | 仅前台，后台不受影响 |

### 6.2 访问控制

| 策略 | 说明 |
|---|---|
| IP 黑名单 | 直接拒绝（返回 403），用于拦截恶意爬虫/攻击源 |
| IP 白名单（可选启用） | 启用后仅白名单可访问官网 |
| UA 拦截 | 关键字/正则拦截（如采集器 UA） |
| 地区/频率限制 | 复用 `express-rate-limit`：官网接口单独一套限流（比管理接口宽松、比客户端严格） |
| 防盗链 | 静态资源 Referer 校验（Nginx 层配置 + 后台白名单域名） |
| 机器人防护 | robots.txt 由后台生成；敏感页面加 `noindex` |

### 6.3 内容与上传安全

| 策略 | 说明 |
|---|---|
| 上传白名单 | 仅允许 jpg/png/webp/svg（svg 需清洗）/gif，单文件大小上限可配 |
| 富文本过滤 | 服务端过滤 `<script>`、`on*` 事件、`iframe`（或仅允许白名单标签） |
| CSP | Nginx + 后端下发 `Content-Security-Policy`，限制外链脚本 |
| XSS/CSRF | 公开接口只读；写接口走 JWT + 同源校验 |
| 后台登录 | 失败次数锁定 + 可选图形验证码 + 登录 IP 记录 |

## 七、数据模型（新增表）

> 命名统一前缀 `site_`，与授权表（`license_keys`、`devices` 等）物理隔离，便于备份与迁移。

| 表 | 关键字段 | 说明 |
|---|---|---|
| `site_settings` | `key`, `value(JSON)`, `group`, `updated_at` | 站点设置 KV（站点名/版权/备案/主色/SEO/统计代码） |
| `site_articles` | `id`, `slug`, `title`, `category`, `cover`, `summary`, `content`, `content_type(md/html)`, `status`, `pinned`, `publish_at`, `seo_title`, `seo_desc`, `views` | 文章/公告统一表，用 `category` 区分；`status=draft/published` |
| `site_cases` | `id`, `industry`, `title`, `summary`, `content`, `avatar`, `metrics(JSON)`, `sort`, `status` | 使用案例 |
| `site_nav` | `id`, `position(top/footer)`, `label`, `url`, `target`, `sort`, `visible` | 导航菜单 |
| `site_contacts` | `id`, `type`, `name`, `value`, `qrcode`, `sort`, `enabled` | 联系方式 |
| `site_media` | `id`, `filename`, `path`, `size`, `mime`, `width`, `height`, `uploaded_by` | 媒体库 |
| `site_download_mirrors` | `id`, `name`, `url`, `sort`, `enabled` | 备用下载镜像 |
| `site_access_rules` | `id`, `type(ip_black/ip_white/ua)`, `pattern`, `note`, `enabled` | 访问控制规则 |
| `site_stats_daily` | `date`, `pv`, `uv`, `downloads`, `buy_clicks` | 官网自身统计（轻量自建，不依赖第三方） |

> 复用已有：`User`（账号）、`OperationLog`（操作审计）、`SystemConfig`（授权平台自身配置，**不与 `site_settings` 混用**）。

## 八、接口设计

### 8.1 公开只读接口 `/api/site/*`（无需登录）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/site/settings` | 站点基本信息（名称/Logo/页脚/备案/公告横幅） |
| GET | `/api/site/nav` | 导航菜单 |
| GET | `/api/site/articles?category=&page=&size=` | 文章列表 |
| GET | `/api/site/articles/:slug` | 文章详情（含 `views` 自增） |
| GET | `/api/site/cases` | 案例列表 |
| GET | `/api/site/contacts` | 联系方式 |
| GET | `/api/site/latest-release` | 最新版本 + 下载地址 + 更新日志（读 `update.json` / 缓存） |
| POST | `/api/site/track` | 埋点：下载点击 / 购买点击（写 `site_stats_daily`） |

### 8.2 管理接口 `/api/admin/site/*`（JWT）

标准 REST CRUD：`articles`、`cases`、`nav`、`contacts`、`media`、`settings`、`access-rules`、`mirrors`，外加：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/site/release/sync` | 从 GitHub 拉取最新 release 信息（只读同步） |
| POST | `/api/admin/site/media/upload` | 上传图片 |
| GET | `/api/admin/site/stats` | 官网访问统计 |
| GET/PUT | `/api/admin/site/security` | 读取/更新安全策略（维护模式、IP 规则等） |

**性能与缓存**：公开接口加 `Cache-Control`（30~60s）+ 内存缓存；`latest-release` 建议缓存 5 分钟，避免每次访问都打 GitHub/CDN。

## 九、技术选型

| 层 | 推荐方案 | 理由 / 备选 |
|---|---|---|

## 十、部署方案

### 10.1 路径规划（已确认：方案 A，不新增二级域名）

当前 `abc222.cn` 根路径是管理后台，本次决定**对调**：

| 路径 | 内容 | 说明 |
|---|---|---|
| `/` | **官网前台** | 对外门面，利于分享与 SEO |
| `/admin/` | 管理后台 | 需要改两处：`vite.config.ts` 加 `base: '/admin/'`；`createWebHistory('/admin/')` |
| `/api/` | 后端 | 不变（客户端 `/api/v1` 不受影响） |

> **方案 A vs 方案 B**：方案 A（本方案）零新增域名，纯靠路径分流，成本最低；方案 B 用 `admin.abc222.cn` 子域名做后台 + 授权平台，官网与后台物理隔离、可分别配 WAF，但需多 1 个 DNS 解析 + 1 张证书 + 1 个 Nginx server 块。**本次采用方案 A**，若后续后台安全要求提升，可平滑迁移到方案 B（后端与数据完全不动，仅 Nginx 层切换）。

### 10.2 Nginx 调整要点（示意）

```nginx
root /www/wwwroot/license-server/website/dist;   # 官网为默认根
index index.html;

# 官网前台（history 路由回退）
location / {
    try_files $uri $uri/ /index.html;
}

# 管理后台（独立静态目录）
location /admin/ {
    alias /www/wwwroot/license-server/admin/dist/;
    try_files $uri $uri/ /admin/index.html;
}

location /api/ {
    proxy_pass http://127.0.0.1:3008;
    # 其余保持现有配置
}
```

### 10.3 构建与发布

- 官网随 `license-server/` 一起走 `update.sh`：拉代码 → 构建 `website` + `admin` + `backend` → 重启 PM2。
- 子仓库同步链路不变（`sync-subrepo.ps1`）。
- 首次上线需在宝塔补一个 `website/dist` 目录与依赖安装。

### 10.4 域名与客户端兼容性（关键约束，不可违背）

**客户端 exe 在编译期硬编码了服务器地址**，无法通过后台批量下发修改：

| 项 | 实测证据 | 结论 |
|---|---|---|
| 内置域名 | `kDefaultServerUrl = L"https://abc222.cn"`（[LicenseServerClient.cpp:19](file:///d:/Projects/2Box-master/eBox/biz/license/LicenseServerClient.cpp#L19)） | 老版本只认 `abc222.cn` |
| 调用接口 | `POST /api/v1/{activate,heartbeat,unbind}`（[766/825/868 行](file:///d:/Projects/2Box-master/eBox/biz/license/LicenseServerClient.cpp#L766)） | 仅这三个 |
| 覆盖方式 | 注册表 `HKCU\Software\2Box\ServerUrl`（[710-714 行](file:///d:/Projects/2Box-master/eBox/biz/license/LicenseServerClient.cpp#L710-L714)） | 仅用于联调，无法推送给全体老用户 |
| 升级通道 | jsDelivr CDN（[MainApp.ixx:189](file:///d:/Projects/2Box-master/eBox/app/MainApp.ixx#L189)） | 与主域名解耦，换域名**不影响**升级 |

> **硬约束**：`abc222.cn` 上的 `location /api/ { proxy_pass http://127.0.0.1:3008; }` **必须永久保留**。官网改版、后台路径调整都不得删除或改道这条反代，否则全体老用户的激活 / 心跳 / 换机立即中断。这是老版本兼容的命脉。

**迁移清单（零数据迁移）**

后端 [.env.example](file:///d:/Projects/2Box-master/license-server/backend/.env.example) 中**不含任何域名绝对 URL**，接口全为相对路径，故调整站点**无需改后端配置、无需动数据库**。实际要做的仅 Nginx 层：

1. **DNS**：方案 A 不新增解析（复用 `abc222.cn`）
2. **SSL**：共用现有证书
3. **Nginx**：`root` 改指官网 dist；新增 `location /admin/`（`alias` 到后台 dist）；**保留 `location /api/`**
4. **后台前端**：加 `base: '/admin/'` 与 `createWebHistory('/admin/')`（两处）

> 注意：`location /admin/` 必须用 `alias` 单独指向后台 dist，不能用 `root` 覆盖，否则会去找「官网dist/admin/」导致 404。

**接口边界（三组物理隔离）**

| 接口组 | 使用者 | 本次处理 |
|---|---|---|
| `/api/v1/*` | 客户端激活 / 心跳 / 换机 | **不动** |
| `/api/admin/*` | 管理后台 | **不动** |
| `/api/site/*` | 官网前台（新增） | **新增** |

> **为什么必须新增 `/api/site/*`**：官网后台要能「更新文章 / 公告 / 站点设置 / 底部版权」。这些内容存于数据库、由后台管理；若官网不调接口读取而全写死在 HTML 里，则后台改内容官网不会变，闭环不成立。该前缀是**全新独立前缀**，与 `/api/v1/*`、`/api/admin/*` 完全隔离，新增对老客户端零风险。

## 附：与授权平台的边界（务必遵守）

1. 官网**只读**授权相关的公开信息（如最新版本）；**绝不**在官网暴露激活码、设备、客户等后台数据。
2. 官网维护模式、限流、IP 拦截**只作用于官网路由与 `/api/site/*`**，不得作用于 `/api/v1/*`（客户端授权）与 `/api/admin/*`（管理后台），避免误伤付费用户与运维。
3. `dist/update.json` 是客户端更新的唯一数据源，官网**不写入**该文件，只读取展示；任何版本信息变更仍走「GitHub Release → Actions 自动更新」原流程。
